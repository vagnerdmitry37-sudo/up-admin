# UPAdmin

## Optimus UI first, for components and for behaviour

Before writing any custom component, logic, styling or workaround, check whether Optimus UI (`@openng/optimus-ui`) already does it. Its docs are https://optimus.openng.org: open the page of the component in use and read its features and examples (for example `https://optimus.openng.org/table#loading-mask`), then confirm the API in `node_modules/@openng/optimus-ui/types/`. Most needs are already built in, both whole components and features of components already in use (loading masks, empty messages, selection, virtual scroll, positioning, animations). Use the built-in feature as the docs show it, with its default look and placement; do not override its styling, position or behaviour unless the user asks. Write custom code only when Optimus has nothing that fits, and say so in your reply with the docs page you checked.

Example: the table loading spinner is `p-table` `[loading]`, which already centres the spinner on the table. A pass-through override that moved the mask was added on a guess, without checking the docs, and was removed.

## Entity operations go only through the action menu

Create, edit, save, delete and any other operation on an entity are done only through the footer action menu (`app-action-menu`), registered with `ActionMenuService.register`. Do not add in-page buttons that perform these operations: not in empty states, forms, table rows or page toolbars. To draw attention to an action, register it with `suggested: true` and, if needed, point to it in text.

### Click actions and hold actions

Each action is defined in one place, `ACTIONS` in `layout/action-menu/action-menu.ts` (a `Record<MenuAction, …>` with label, icon and trigger kind, in arc order), so a new `MenuAction` without a full entry fails the build. The trigger kind is: `click` (create, edit) runs on a normal click; `hold` (save, delete) runs only after the button is pressed and held for `DEFAULT_HOLD_DURATION_MS` (800 ms). Releasing, leaving the button or losing focus before then cancels it. Keyboard users hold Enter or Space. Registrations never choose the kind: they only supply `click`, and the menu decides how it is triggered.

The input handling lives in `shared/action-trigger` (`ActionTrigger`, `[appActionTrigger]="kind"`, emits `triggered`). While holding it adds `action-trigger-holding`, sets `--action-trigger-hold-progress` (0 to 1) on the host and exposes `holding()` and `holdProgress()` (`exportAs: 'actionTrigger'`). While holding, `ActionMenu` shows `<app-progress-ring [value]="trigger.holdProgress()" />`, a ring that fills clockwise from the top, so the user sees how much of the hold is left; once the action runs the hold ring goes away. It can be put on any button that needs a hold.

### Running state of an action

There is no running flag of the menu's own: `HttpActivity` is the only source. An action's `click` returns the promise of its request (Save: `save()`, Delete: `deleteEntities(ids)` or the image `delete`); `ActionMenuService.run` wraps it in `HttpActivity.track({ entity, operation: action, source: 'action-menu' }, click)`, an operation that runs until the promise settles. Consumers read it directly: `isRunning({ source: 'action-menu' })` for "any action is running", `isRunning({ source: 'action-menu', operation: action })` for one action (see Request activity). Only `run` sets that source, so other `track` callers never lock the menu. Every registration names its `entity` (`register({ entity: () => …, actions })`): the entity pages pass `entityName`, `ImageUpload` passes `'image'`. Components never keep their own `saving` / `deleting` flags. While an action runs:

- the action stays listed even if its page now marks it not `visible` (Save after the forms turn pristine, Delete after the selection is cleared);
- `run` ignores every action, so nothing runs twice or alongside it;
- `EntityEditPage` disables closing tabs (`actionRunning`).

### Action status indicator

Actions that send a request (`save`, `delete`; `REQUEST_ACTIONS` in `core/action-menu.service.ts`) show their progress on their own menu button, after the hold ring: spinner, then success or error. `ActionMenuService` derives a display status per action (`status`, `ActionStatus`) from `HttpActivity.on({ kind: 'operation', source: 'action-menu' })`, so HttpActivity stays the source of truth and the status only adds display timing:

- `running` from the operation's start, which is the moment the hold ring reaches 100%, so the spinner never shows early. It lasts at least `MINIMUM_SPINNER_DURATION_MS` (1000 ms), or until the request completes if that takes longer.
- Then `succeeded` or `failed` for `RESULT_DURATION_MS` (1500 ms), then no status. A `cancelled` operation shows no result.
- Hold shows the hold ring (`app-progress-ring`) and running shows Optimus's `p-progressspinner`, styled to match the ring: same circle (viewBox `25 25 50 50`, radius 20), `strokeWidth="3"`, the same `inset: -8.14%` box (`.action-menu-spinner`), and the primary colour (`NoirPreset` sets all four `progressspinner` colour tokens to `{primary.color}` instead of Aura's red, blue, green and yellow). It is `aria-hidden`; the button's label and `aria-busy` carry the state. The result is only an icon on the plain button, with no ring, because a full ring around a finished action read as a heavy border. Everything uses the menu's own black and grey; the button stays `severity="secondary"` and keeps its size.

  | Stage   | Ring                                                                                               | Icon                |
  | ------- | -------------------------------------------------------------------------------------------------- | ------------------- |
  | Hold    | fills clockwise                                                                                    | the action's icon   |
  | Running | `p-progressspinner` (built-in rotation and dash animation), at least `MINIMUM_SPINNER_DURATION_MS` | the action's icon   |
  | Success | none                                                                                               | `OpenngIcons.CHECK` |
  | Error   | none                                                                                               | `OpenngIcons.TIMES` |

  No green, red, severity colours or spinner icons: a separate shape per stage read as three different components. The icon is set through `pButton`'s own `[icon]` input, not a projected `pButtonIcon`, because the directive then recomputes its classes (including `p-button-icon-only`, which sets the button's size) whenever the icon changes. A projected icon plus a later `severity` change strips that class for good. The `aria-label` gets "in progress", "done" or "failed", and `aria-busy` is set while running. No messages are shown here; the request error toast still covers failures.

- An action stays listed while it has a status, so Save and Delete stay visible through their result even though the forms turned pristine or the selection was cleared. When the result ends, a hidden action keeps its last result icon (`lastResult`) through the speed dial's exit animation, so the action icon never flashes back between the result and the action leaving. A visible action shows its own icon again.
- `run` ignores every action while any status is `running` (the spinner means busy), and it ignores an action listed only because of its status (`visible: false`). The result phase does not lock the menu.
- Create and Edit send no request and show no status.

Saving with Enter in a form goes through the same path: `EntityForm` calls `EntityEditPage.submit`, which calls `run('save')`.

`shared/progress-ring` (`ProgressRing`, `app-progress-ring`) is a ring drawn inside its button that fills clockwise from the top to `value` (0 to 1): the stroke's outer edge lies on the button's edge, so it reads as the button's own border and never reaches past it, and the button keeps its size and position whether the ring shows or not. The ring is absolutely positioned (no layout effect); its box is `inset: -8.14%` because its circle (radius 20, stroke 3, viewBox 50) has its outer edge at 43% of the box, and 0.5 / 0.43 = 1.163 of the button. Its color is `--app-progress-ring-color`, the primary color, over a full-circle track in `--app-progress-ring-track-color` (`--p-content-border-color`); the Noir theme is monochrome, so the foreground color gives the highest contrast. Because it is flush and primary, it is only drawn around `severity="secondary"` buttons. It is decorative (`aria-hidden`); the parent must be `position: relative`, and the ring must be a sibling of a button, not its child, because Optimus buttons have `overflow: hidden` and would clip it. Wrap the button and ring in their own `position: relative; display: flex` element so the ring is sized to the button alone (`ActionMenu` uses `.action-menu-action`).

### Loading indicator on tables

Loading is shown only on the table that is loading, with Optimus's built-in table loading mask and spinner (`p-table` `[loading]`), never with a page-level or footer spinner. `DataTable` and `EntityTable` take a `loading` input and pass it through. `EntityPage` computes it from `HttpActivity`: `isRunning({ kind: 'request', entity: entityName(), method: 'GET' })`, so the first page, every lazily loaded range while scrolling and the reload after Delete all show it, and nothing keeps a `loading` flag of its own. The table is rendered from the start (`rows ?? []`) so the spinner shows during the first load; the empty state replaces it only once the first page came back empty. While loading, `DataTable` reserves at least one body row of height, so the mask over an empty table has room for the spinner. Save and Delete show their progress on their action menu button (see Action status indicator); image upload and reorder have no busy indicator yet.

## Request errors are shown globally

There are exactly two kinds of error display:

- **Form validation errors** are shown in the form, at the invalid field (`app-field-frame`'s reserved error line).
- **Every other error** (failed requests, rejected uploads, unexpected exceptions) is shown only as a toast through `AppMessageService.error(summary, detail)` (`core/app-message.service.ts`). It wraps Optimus's `MessageService`, which is injected only there; app code never calls `MessageService.add` directly. Warning and info methods will be added to `AppMessageService` the same way when needed. How long a toast stays is set once for the whole app by `messageLife` (8 s) on the `p-toast` in `Shell`; messages never pass their own `life`. Such errors are never shown as an inline message, banner or error block in a page. After such an error a page falls back to a neutral state (for example an empty table), not a blank screen. Uncaught exceptions reach `core/app-error-handler.ts` (`AppErrorHandler`, registered as Angular's `ErrorHandler`), which shows a generic toast; it skips `HttpErrorResponse` because the request error listener below already showed one.

Every failed API request is turned into one Optimus toast (`p-toast` in `Shell`, fed through `AppMessageService.error`) by `core/request-error-toasts.ts` (`provideRequestErrorToasts()` in `app.config.ts`), a listener on the failed requests of `HttpActivity`, so pages never catch HTTP errors to show a message. It maps the status to a plain-language summary: 0 no connection, 400 the validation messages, 403 not allowed, 404 refresh and try again, 409 the server `detail`, 5xx try again later. It skips 401, which `authInterceptor` and `SessionService` handle, and any status the request lists in its tag's `handledStatuses`: login passes `[400]`, which `LoginPage` shows inline as rejected credentials, so a failed login (no connection, 5xx) still gets a toast. Token refresh and logout are untracked, so they never toast. The error still reaches the caller, so callers still stop. Write server `detail` texts for 409 so a user can read them.

## Request activity is tracked centrally

`core/http-activity.service.ts` (`HttpActivity`) is the single source of truth for everything in flight: every HTTP request and every operation started through `track`, each with the entity it belongs to. Spinners, locks, loading states and error toasts read it; nothing else keeps its own request bookkeeping.

- Each entry is an `Activity` `{ id, kind, entity, operation, source, method, url, status, error }`. `kind` is `request` (one HTTP call with its `method`, recorded by `core/http-activity.interceptor.ts`, registered first in `app.config.ts`, so it sees the final outcome after auth's refresh and retry) or `operation` (one user action that may send several requests, from `track({ entity, operation, source }, work)`; `operation` is a free name such as `'save'` or `'upload'`). It starts as `running` and ends exactly once as `succeeded`, `failed` (with `error`) or `cancelled` (unsubscribed before a response, for example after leaving the page).
- All HTTP goes through `core/api-client.ts` (`ApiClient`); nothing else injects `HttpClient` (enforced by ESLint, specs excepted). A service takes a client per entity, `private readonly api = inject(ApiClient).forEntity('product')` (more for other entities it calls: `imageApi`, `customerApi`), and calls `get` / `post` / `put` / `delete` with `params` and, where needed, `handledStatuses` or `untracked`; `resource(url)` wraps `httpResource`. The client puts the entity on the request, so every request is tagged and call sites never build an `HttpContext`. `ActivityEntity` uses the same words as `entityName` (`'order item'`), so entity pages pass `entityName` straight through; a new entity is added there.
- Read it with `running` or `isRunning(filter?)` inside a `computed` or template (for example `isRunning({ entity: 'image', method: 'POST' })` or `isRunning({ source: 'image-upload' })`); subscribe with `on(filter)` (for example `on({ entity: 'product', status: 'succeeded' })`) or `changes`. A filter matches on any of `kind`, `entity`, `operation`, `source`, `method`, `status`. `source` (`ActivitySource`) names the UI piece that started an operation through `track`: `'action-menu'` (every menu action) and `'image-upload'` (`ImageUpload`'s upload and reorder; its delete runs through the action menu). Sources are set where the UI starts the work, never in feature services, which do not know their caller. Add a source together with the code that sets and reads it.
- `{ untracked: true }` opts a request out: token refresh and logout use it; login is tracked as a `session` request.

## Entity features are mirrors: orders, products, customers

`src/app/features/orders`, `src/app/features/products` and `src/app/features/customers` are the same feature built for three entities. They must stay structurally identical. Any change to one of them is applied to all three in the same change, unless the entity truly cannot support it; in that case say so explicitly to the user instead of silently diverging.

### Shared shape (`<entity>` = order | product | customer)

| Piece      | Location               | Convention                                                                                                                                                                                                                                                                  |
| ---------- | ---------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| List route | `app.routes.ts`        | `path: '<entity>s'`, title `<Entity>s · UP`, `data: { heading: '<Entity>s' }` (routes are typed `AppRoute`, so wrong keys or values fail the build)                                                                                                                         |
| Edit route | `app.routes.ts`        | `path: 'edit-<entity>s-page'`, no path params, `data: { heading: '<Entity>s', editPage: true }`                                                                                                                                                                             |
| List page  | `<entity>s-page/`      | `loadPage = <Entity>sService.list`, `deleteEntities = <Entity>sService.delete` and `columns`; template is only `<app-entity-page [loadPage]="loadPage" [deleteEntities]="deleteEntities" [columns]="columns" editPath="/edit-<entity>s-page" entityName="<entity>" />` |
| Edit page  | `edit-<entity>s-page/` | `readonly ids = input<string>()`, `load<Entity>s = <Entity>sService.get`, `<entity>Name`, `<entity>Writer` (`EntityWriter` with `create` and `update`); template is only `<app-entity-edit-page>` with one `<ng-template let-<entity>>` holding the form                    |
| Service    | `<entity>s.service.ts` | same method names across entities                                                                                                                                                                                                                                           |
| Form       | `<entity>-form/`       | used by the edit page                                                                                                                                                                                                                                                       |

The footer shows the page heading next to the nav menu button (`layout/page-heading`, `PageHeading`). It reads `heading` from the deepest active route's data, so nested components such as the order items table cannot change it. On a route with `editPage: true` it adds `Editor` as a muted word after a separator (`Orders / Editor`), the same whether the tabs hold saved records, new ones or both, because one edit page mixes creating and editing. The word is text, not an icon in a circle, because round elements in the footer are buttons. Routes without `heading` (not found) show no heading.

Selected IDs travel as the `ids` query param (`/edit-products-page?ids=1,2`), bound to the edit page's `ids` input by `withComponentInputBinding()`. Do not add `:id` path params: the edit pages open several records as tabs, and a required path segment would break `/edit-products-page` without IDs.

### Developer steps for any change touching one entity feature

1. Make the change in the entity you were asked about.
2. Apply the equivalent change to the other two entities: routes, list page, edit page, service, form, templates, styles.
3. Keep names parallel (`ProductsPage` / `OrdersPage` / `CustomersPage`, `productName` / `orderNumber` / `customerName`, and so on).
4. Search all three features for the old name, path or pattern to confirm nothing was left behind.
5. Report which entity could not follow and why, if any.

### Known gaps between the three (close them, do not copy them)

- None open.

### Deleting lives in `EntityPage`

Entities are deleted only from the list table: select one or more rows, hold Delete in the action menu (registered by `EntityTable`, which runs its `deleteRows` input). There is no confirmation dialog: the press-and-hold is the safeguard. The list page's `delete` then calls `deleteEntities(ids)` (one bulk DELETE), clears the selection and reloads the table; the table shows its loading spinner while the reload runs (see Loading indicator on tables). Customers that still have orders are refused by the API with 409.

### Edit page logic lives in `EntityEditPage`

`shared/entity/entity-edit-page` owns everything the three edit pages share; entity pages only supply `ids`, `load`, `label`, `entityName` (same word as the list page's, used for the "New …" tab), `writer` (`create` and `update`, both required), `listPath` and the form template. Shared behaviour (creating and updating) goes there, not into the entity pages. Deleting is not done here: it lives in `EntityPage`.

- With `ids`: loads the records and shows one tab per record, rendering the template with the record. The tab bar is shown for any number of records, one included, so the layout never jumps while tabs are closed. Every tab has the same fixed width (12rem, in `shared/entity/entity-tabs`), so a tab never resizes when its record is renamed and saved; a longer name is cut with an ellipsis and shown in full as the label's `title` tooltip (the close button's `aria-label` also carries the full name). The tab bar is `scrollable`, but Optimus's `TabList` only rechecks its ‹ › arrows when its own box resizes or the strip is scrolled, and a `Tab` scrolls itself into view only on keyboard navigation, not when it is shown by code (Create, or Save swapping `new-N` for the record id). So `EntityTabs` runs an `afterRenderEffect` on the `Tab` query (`viewChildren(Tab)`) and the shown tab's `active()` that calls Optimus's own `Tab.scrollInView` and `TabList.updateButtonState()`. It tracks the `Tab` instances, not `entities`: `@for … track entity.id` keeps them across reloads, so reloading records after Save does not rerun it and scroll the page back to the tab bar.
- Each tab has a close button (×). It is disabled, not hidden, while any menu action is running, so tabs never change width. Closing the last open tab navigates to `listPath` (with `replaceUrl`): `/<entity>s` for the three entities, the order's edit page for order items. Closing only removes the id from `?ids` (with `replaceUrl`, so Back does not reopen it); it never deletes the record, and it is a view action, so it may live on the tab instead of the action menu. A tab with unsaved changes asks first (Discard / Keep editing) in the shared `p-confirmdialog` (in `Shell`, driven by `ConfirmationService`); this is its only remaining use. Closing the shown tab shows its right neighbour, or the left one if it was last. Removing ids does not reload the records (`loadedIds` ignores subsets), so unsaved edits in the other tabs survive. The × is focusable only on the active tab and stops Enter and Space from reaching `p-tab`, which would otherwise cancel its click.
- New records are tabs too: each is a `new-N` token in `?ids` next to the record ids (`?ids=12,34,new-1`; helpers `isNewEntityId`, `nextNewEntityId`, `firstNewEntityId` in `shared/route-ids`). A new tab is an `EntityTab` with `entity: undefined`, labelled "New `<entityName>`", and renders the template with `undefined`, so the form is empty. Without `ids` the page shows one new tab (`new-1`). New and saved tabs mix freely, in URL order; only real ids are passed to `load`, and the last loaded records are kept while new ids load, so tabs never unmount mid-save.
- Create is always in the action menu on an edit page (registered by `EntityEditPage`): it appends the next `new-N` to `?ids` (with `replaceUrl`) and shows that tab, so a user editing several records can start new ones beside them. Closing a new tab drops its token like any other; closing the last tab goes to `listPath`.
- Forms and parts are matched to their tab by tab id, not entity id, because every new tab has no entity id. Each tab's template gets its own injector providing `ENTITY_TAB_ID` (the tab's id); `EntityForm.tabId` and `EntityEditPart.tabId` read it. Injectors are cached per tab id and pruned only after the navigation that removes their ids (`pruneTabInjectors`): `NgTemplateOutlet` rebuilds its view when the injector changes, so dropping one while its tab is still rendered would recreate that tab's form empty.
- Save appears while any open form or part is dirty. It validates the dirty forms plus each new tab's form whose parts are dirty (`EntityForm.validValue`), because a record must exist before its parts can be saved. A new tab nobody touched is skipped. If one is invalid, nothing is sent and its tab is shown.
- A part (`EntityEditPart`: `tabId`, `dirty`, `save(entityId)`) is anything besides the form that holds pending changes for a record and saves them only on Save, so every write of an edit page goes through the Save action. Parts connect through DI (`connectPart` / `disconnectPart`), like forms, so `EntityEditPage` stays generic (today the only part is `ImageUpload`). A tab whose part is dirty asks before closing, like a dirty form.
- Save first calls `writer.update(changes)` once with every changed saved record (`EntityChange`: the loaded entity and the form value), which maps them to one bulk PUT (all or nothing), and saves the dirty parts of saved tabs with their record id. It then calls `writer.create(value)` for each new tab in turn and saves that tab's dirty parts with the new id (a failed part does not undo the create). Finally it replaces every created `new-N` in `?ids` with its record id, keeping tab order and the shown tab, which loads the new records; until they arrive, each created id keeps a tab with `entity: undefined` (`createdIds`), so the tab does not vanish and the shown tab does not jump. If nothing was created it reloads the records instead, also when the update or a part save fails, so parts that did save (uploaded images) are not staged again. If a create fails, the records already created still get their ids, the failed tab stays new with its input, and the request error toast shows.
- `EntityForm` connects itself to the enclosing `EntityEditPage` through DI (`connect` / `disconnect`) and reports `dirty`, so entity forms need no create- or update-specific code.

### Form fields never read layout while rendering

Optimus inputs (`p-iftalabel` labels, input borders) have CSS transitions, so if the browser computes their style before Angular has set their host classes, they animate from browser defaults (a 16px dark label shrinking to 12px, a dark border fading). That happens whenever something reads layout (`scrollHeight`, `offsetWidth`, `getBoundingClientRect`) in the middle of rendering a view, such as in `ngAfterViewInit` / `ngAfterViewChecked` of a field placed before others. Optimus's `pTextarea` `autoResize` does exactly that, so `TextareaField` does not use it: it calls `Textarea.resize()` from an `afterRenderEffect` (`mixedReadWrite`) on the control's value and `rows`, plus a width `ResizeObserver`. Size things after render (`afterRenderEffect`, `afterNextRender`, `ResizeObserver`), never inside lifecycle hooks.

### Images live in `ImageUpload`

`shared/image-upload` (`ImageUpload`, `app-image-upload`) holds everything about an entity's images and is generic, like the images API (`entityType` + `entityId`); `EntityEditPage` knows nothing about images. The edit page passes `entityId`, `savedImages` and an `ImageWriter` (`upload`, `delete`, `reorder`) built from its feature service, as `EditProductsPage.productImageWriter` does with `ProductsService`. Writes follow the action menu like everything else: new images are saved by Save and removed by Delete; only reordering saved images is sent straight away, because it is a view arrangement rather than new data:

- The gallery is one grid: the image cards, then an "Add images" upload card that always stays last (it is a disabled `cdkDrag`, and `keepsUploadCardLast` stops images from being sorted into its slot). Clicking it opens the file picker; files can also be dropped anywhere on the gallery.
- Choosing or dropping files only stages them, on new and saved records alike: they appear as cards at once (object-URL previews, `id` `staged-N`, `stagedFile` set), the component turns `dirty` and Save appears. The component is an `EntityEditPart`: its `save(entityId)` uploads the staged files in one request (so at most 10 can be staged) and, if the user dragged staged cards between saved ones, sends one `reorder` with the final order. The page then reloads or reopens the record, and `images` (a `linkedSignal` of `savedImages`) resets to the saved list, which drops the staged entries.
- Rejected files are never shown inside the component: FileUpload's own type and size messages (worded through its `invalidFile*Message*` inputs) are moved into the global error toast via `AppMessageService.error` ("Image not added", one toast per file), and the component checks the 10-files-per-upload limit itself, because FileUpload adds that message only after `onSelect`.
- Dragging changes the order on screen at once. If the order of the saved images changed, it calls `reorder` straight away with the saved ids only (`PUT /api/images/order` must list exactly the current saved images) and puts the old order back if the request fails; staged images are placed on Save.
- Selecting images shows Delete in the action menu, registered by the component itself; holding it calls `delete` for the selected saved images without a confirmation dialog and drops selected staged images locally.
- A new record shows the gallery from the start, so images can be added together with the other fields; Save creates the record first and then uploads them. A failed image upload does not undo the create: the request error toast shows, the record reopens without those images, and the user adds them again.
- Each card shows the image's original `fileName` (stored by the API on upload). Images uploaded before the API stored names have an empty `fileName` and show "Image N" (their position) instead.

Today only products use it; orders and customers have no images. To add images to another entity, give its service the three image calls and pass a writer the same way.
