# UPAdmin

## Entity operations go only through the action menu

Create, edit, save, delete and any other operation on an entity are done only through the footer action menu (`app-action-menu`), registered with `ActionMenuService.register`. Do not add in-page buttons that perform these operations: not in empty states, forms, table rows or page toolbars. To draw attention to an action, register it with `suggested: true` and, if needed, point to it in text.

### Click actions and hold actions

Each action is defined in one place, `ACTIONS` in `layout/action-menu/action-menu.ts` (a `Record<MenuAction, …>` with label, icon and trigger kind, in arc order), so a new `MenuAction` without a full entry fails the build. The trigger kind is: `click` (create, edit) runs on a normal click; `hold` (save, delete) runs only after the button is pressed and held for `DEFAULT_HOLD_DURATION_MS` (800 ms). Releasing, leaving the button or losing focus before then cancels it. Keyboard users hold Enter or Space. Registrations never choose the kind: they only supply `click`, and the menu decides how it is triggered.

The input handling lives in `shared/action-trigger` (`ActionTrigger`, `[appActionTrigger]="kind"`, emits `triggered`). While holding it adds `action-trigger-holding`, sets `--action-trigger-hold-progress` (0 to 1) on the host and exposes `holding()` and `holdProgress()` (`exportAs: 'actionTrigger'`). While holding, `ActionMenu` shows `<app-progress-ring [value]="trigger.holdProgress()" />`, a ring that fills clockwise from the top, so the user sees how much of the hold is left; once the action runs the hold ring goes away and the nav menu's loading ring shows the work (see Busy indicator on the nav menu button). It can be put on any button that needs a hold.

### Running state of an action

There is no running flag of the menu's own: `HttpActivity` is the only source. An action's `click` returns the promise of its request (Save: `save()`, Delete: `deleteEntities(ids)` or the image `delete`); `ActionMenuService.run` wraps it in `HttpActivity.track({ entity, operation: action, source: 'action-menu' }, click)`, an operation that runs until the promise settles. Consumers read it directly: `isRunning({ source: 'action-menu' })` for "any action is running", `isRunning({ source: 'action-menu', operation: action })` for one action (see Request activity). Only `run` sets that source, so other `track` callers never lock the menu. Every registration names its `entity` (`register({ entity: () => …, actions })`): the entity pages pass `entityName`, `ImageUpload` passes `'image'`. Components never keep their own `saving` / `deleting` flags. While an action runs:

- the action stays listed even if its page now marks it not `visible` (Save after the forms turn pristine, Delete after the selection is cleared);
- `run` ignores every action, so nothing runs twice or alongside it;
- `EntityEditPage` disables closing tabs (`actionRunning`).

Saving with Enter in a form goes through the same path: `EntityForm` calls `EntityEditPage.submit`, which calls `run('save')`.

`shared/progress-ring` (`ProgressRing`, `app-progress-ring`) is a ring drawn inside its button: the stroke's outer edge lies on the button's edge, so it reads as the button's own border and never reaches past it, and the button keeps its size and position whether the ring shows or not. The ring is absolutely positioned (no layout effect); its box is `inset: -8.14%` because the Optimus spinner's circle (radius 20, stroke 3, viewBox 50) has its outer edge at 43% of the box, and 0.5 / 0.43 = 1.163 of the button. Its color is `--app-progress-ring-color`, the primary color (near black in light mode, near white in dark), over a full-circle track in `--app-progress-ring-track-color` (`--p-content-border-color`). The Noir theme is monochrome, so the ring uses the foreground color rather than a lone accent hue: it has the highest contrast against the page (well above the 3:1 that WCAG 1.4.11 asks of indicators), where mid grey fell short. Because it is flush and primary, it is only drawn around `severity="secondary"` buttons (light grey). Around a primary (black) button it would merge with the button, so such a button switches to secondary while its ring shows, rather than the ring changing color or moving away. The track keeps the shape of a ring readable while the spinner's arc is short. Without `value` the Optimus `p-progress-spinner` (work of unknown length) turns over the track; with `value` (0 to 1) its own SVG fill covers that fraction of the track, because Optimus has no determinate circular progress. It is decorative (`aria-hidden`); the parent must be `position: relative` and set `aria-busy` itself, and the ring must be a sibling of a button, not its child, because Optimus buttons have `overflow: hidden` and would clip it. Wrap the button and ring in their own `position: relative; display: flex` element so the ring is sized to the button alone (`ActionMenu` uses `.action-menu-action`, `NavMenu` uses `.nav-menu-trigger`); a component host is usually taller than its button, which pushes the ring off-centre and out of the footer, adding a page scrollbar. The ring's host has `overflow: hidden`: Optimus rotates a square SVG, whose corners reach about 40% past the ring while it turns and would otherwise add a page scrollbar; the circle lies inside the square, so clipping removes nothing visible. Use it for any round button that shows work in progress.

The ring is always rendered and decides itself when to draw: with `value` it shows the fill; with `[running]="…"` it spins. A spinning ring stays for at least one full turn, `SPINNER_TURN_MS` (2 s, inside `progress-ring.ts`), so a fast request never flashes a fragment of the ring: it starts as soon as `running` turns true and stops no sooner than one turn after it started. The same constant is the spinner's `animationDuration`, so a turn and the minimum always match. The component exposes that stretched state as `spinning()` (`exportAs: 'progressRing'`), so whatever else must follow the ring, such as the button's busy colour and `aria-busy`, reads `ring.spinning()` from a template reference instead of the raw activity, and never comes apart from it. It only delays the ring: locks such as `run` and `EntityEditPage.actionRunning` read `HttpActivity` directly.

### Busy indicator on the nav menu button

The app has one busy indicator: while any request is in flight, `NavMenu` (`layout/nav-menu`) draws the spinning `app-progress-ring` around its button and sets `aria-busy`. The button is primary (black) at rest and looks secondary (light grey, like the action menu's actions) while the ring shows, so the primary ring stands out against it; the colour change is itself part of the busy signal. It switches through the `trigger-busy` class, which points the `--p-button-primary-*` tokens at their `--p-button-secondary-*` values, never by binding `severity`: changing `severity` after first render makes Optimus rebuild the button's classes and drop `p-button-icon-only`, so the round button turns into a pill. It passes `busy` (`HttpActivity.isRunning({ kind: 'request' })`) to `<app-progress-ring #ring="progressRing" [running]="busy()" />` and binds the button's `trigger-busy` class and `aria-busy` to `ring.spinning()`, so loading (entity lists, records, product types) and writing (Save, Delete, image upload and reorder) all show there. Action buttons draw no running ring of their own, only the hold ring while being held; a second ring would duplicate this one. Pages keep no `loading` flags of their own for it. The nav menu button sits in the footer on every page, so the indicator stays in the same place whichever page is busy.

## Request errors are shown globally

There are exactly two kinds of error display:

- **Form validation errors** are shown in the form, at the invalid field (`app-field-frame`'s reserved error line).
- **Every other error** (failed requests, rejected uploads, unexpected exceptions) is shown only as a toast through `AppMessageService.error(summary, detail)` (`core/app-message.service.ts`). It wraps Optimus's `MessageService`, which is injected only there; app code never calls `MessageService.add` directly. Warning and info methods will be added to `AppMessageService` the same way when needed. How long a toast stays is set once for the whole app by `messageLife` (8 s) on the `p-toast` in `Shell`; messages never pass their own `life`. Such errors are never shown as an inline message, banner or error block in a page. After such an error a page falls back to a neutral state (for example an empty table), not a blank screen. Uncaught exceptions reach `core/app-error-handler.ts` (`AppErrorHandler`, registered as Angular's `ErrorHandler`), which shows a generic toast; it skips `HttpErrorResponse` because the request error listener below already showed one.

Every failed API request is turned into one Optimus toast (`p-toast` in `Shell`, fed through `AppMessageService.error`) by `core/request-error-toasts.ts` (`provideRequestErrorToasts()` in `app.config.ts`), a listener on the failed requests of `HttpActivity`, so pages never catch HTTP errors to show a message. It maps the status to a plain-language summary: 0 no connection, 400 the validation messages, 403 not allowed, 404 refresh and try again, 409 the server `detail`, 5xx try again later. It skips 401, which `authInterceptor` and `SessionService` handle, and any status the request lists in its tag's `handledStatuses`: login passes `[400]`, which `LoginPage` shows inline as rejected credentials, so a failed login (no connection, 5xx) still gets a toast. Token refresh and logout are untracked, so they never toast. The error still reaches the caller, so callers still stop. Write server `detail` texts for 409 so a user can read them.

## Request activity is tracked centrally

`core/http-activity.service.ts` (`HttpActivity`) is the single source of truth for everything in flight: every HTTP request and every operation started through `track`, each with the entity it belongs to. Spinners, locks, loading states and error toasts read it; nothing else keeps its own request bookkeeping.

- Each entry is an `Activity` `{ id, kind, entity, operation, source, method, url, status, error }`. `kind` is `request` (one HTTP call with its `method`, recorded by `core/http-activity.interceptor.ts`, registered first in `app.config.ts`, so it sees the final outcome after auth's refresh and retry) or `operation` (one user action that may send several requests, from `track({ entity, operation, source }, work)`; `operation` is a free name such as `'save'` or `'upload'`). It starts as `running` and ends exactly once as `succeeded`, `failed` (with `error`) or `cancelled` (unsubscribed before a response, for example after leaving the page).
- All HTTP goes through `core/api-client.ts` (`ApiClient`); nothing else injects `HttpClient` (enforced by ESLint, specs excepted). A service takes a client per entity, `private readonly api = inject(ApiClient).forEntity('product')` (more for other entities it calls: `imageApi`, `customerApi`), and calls `get` / `post` / `put` / `delete` with `params` and, where needed, `handledStatuses` or `untracked`; `resource(url)` wraps `httpResource`. The client puts the entity on the request, so every request is tagged and call sites never build an `HttpContext`. `ActivityEntity` uses the same words as `entityName` (`'order item'`), so entity pages pass `entityName` straight through; a new entity is added there.
- Read it with `running` or `isRunning(filter?)` inside a `computed` or template (for example `isRunning({ entity: 'image', method: 'POST' })` or `isRunning({ source: 'image-upload' })`); subscribe with `on(filter)` (for example `on({ entity: 'product', status: 'succeeded' })`) or `changes`. A filter matches on any of `kind`, `entity`, `operation`, `source`, `method`, `status`. `source` (`ActivitySource`) names the UI piece that started an operation through `track`: `'action-menu'` (every menu action) and `'image-upload'` (`ImageUpload`'s upload and reorder; its delete runs through the action menu). Sources are set where the UI starts the work, never in feature services, which do not know their caller. Add a source together with the code that sets and reads it.
- `{ untracked: true }` opts a request out: token refresh and logout use it; login is tracked as a `session` request.

## Entity features are mirrors: orders, products, customers

`src/app/features/orders`, `src/app/features/products` and `src/app/features/customers` are the same feature built for three entities. They must stay structurally identical. Any change to one of them is applied to all three in the same change, unless the entity truly cannot support it; in that case say so explicitly to the user instead of silently diverging.

### Shared shape (`<entity>` = order | product | customer)

| Piece      | Location               | Convention                                                                                                                                                                                                                                                                  |
| ---------- | ---------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| List route | `app.routes.ts`        | `path: '<entity>s'`, title `<Entity>s · UP`, `data: { heading: '<Entity>s' } satisfies PageHeadingData`                                                                                                                                                                     |
| Edit route | `app.routes.ts`        | `path: 'edit-<entity>s-page'`, no path params, `data: { heading: '<Entity>s', editPage: true } satisfies PageHeadingData`                                                                                                                                                   |
| List page  | `<entity>s-page/`      | `loadPage = <Entity>sService.list`, `deleteEntities = <Entity>sService.delete` and `columns`; template is only `<app-entity-list-page [loadPage]="loadPage" [deleteEntities]="deleteEntities" [columns]="columns" editPath="/edit-<entity>s-page" entityName="<entity>" />` |
| Edit page  | `edit-<entity>s-page/` | `readonly ids = input<string>()`, `load<Entity>s = <Entity>sService.get`, `<entity>Name`, `<entity>Writer` (`EntityWriter` with `create` and `update`); template is only `<app-entity-edit-page>` with one `<ng-template let-<entity>>` holding the form                    |
| Service    | `<entity>s.service.ts` | same method names across entities                                                                                                                                                                                                                                           |
| Form       | `<entity>-form/`       | used by the edit page                                                                                                                                                                                                                                                       |

The footer shows the page heading next to the nav menu button (`layout/page-heading`, `PageHeading`). It reads `heading` from the deepest active route's data, so nested components such as the order items table cannot change it. On a route with `editPage: true` it adds the current action as a muted word after a separator: `Orders / Edit` when the URL has `ids`, `Orders / New` when it has none. The action is text, not an icon in a circle, because round elements in the footer are buttons. Routes without `heading` (not found) show no heading.

Selected IDs travel as the `ids` query param (`/edit-products-page?ids=1,2`), bound to the edit page's `ids` input by `withComponentInputBinding()`. Do not add `:id` path params: the edit pages open several records as tabs, and a required path segment would break `/edit-products-page` without IDs.

### Developer steps for any change touching one entity feature

1. Make the change in the entity you were asked about.
2. Apply the equivalent change to the other two entities: routes, list page, edit page, service, form, templates, styles.
3. Keep names parallel (`ProductsPage` / `OrdersPage` / `CustomersPage`, `productName` / `orderNumber` / `customerName`, and so on).
4. Search all three features for the old name, path or pattern to confirm nothing was left behind.
5. Report which entity could not follow and why, if any.

### Known gaps between the three (close them, do not copy them)

- None open.

### Deleting lives in `EntityListPage`

Entities are deleted only from the list table: select one or more rows, hold Delete in the action menu (registered by `EntityTable`, which runs its `deleteRows` input). There is no confirmation dialog: the press-and-hold is the safeguard. The list page's `delete` then calls `deleteEntities(ids)` (one bulk DELETE), clears the selection and reloads the table; the nav menu's busy ring spins until that finishes (see Busy indicator on the nav menu button). Customers that still have orders are refused by the API with 409.

### Edit page logic lives in `EntityEditPage`

`shared/entity-edit-page` owns everything the three edit pages share; entity pages only supply `ids`, `load`, `label`, `entityName` (same word as the list page's, used for the "New …" tab), `writer` (`create` and `update`, both required), `listPath` and the form template. Shared behaviour (creating and updating) goes there, not into the entity pages. Deleting is not done here: it lives in `EntityListPage`.

- With `ids`: loads the records and shows one tab per record, rendering the template with the record. The tab bar is shown for any number of records, one included, so the layout never jumps while tabs are closed.
- Each tab has a close button (×). It is disabled, not hidden, while any menu action is running, so tabs never change width. Closing the last open tab navigates to `listPath` (with `replaceUrl`): `/<entity>s` for the three entities, the order's edit page for order items. Closing only removes the id from `?ids` (with `replaceUrl`, so Back does not reopen it); it never deletes the record, and it is a view action, so it may live on the tab instead of the action menu. A tab with unsaved changes asks first (Discard / Keep editing) in the shared `p-confirmdialog` (in `Shell`, driven by `ConfirmationService`); this is its only remaining use. Closing the shown tab shows its right neighbour, or the left one if it was last. Removing ids does not reload the records (`loadedIds` ignores subsets), so unsaved edits in the other tabs survive. The × is focusable only on the active tab and stops Enter and Space from reaching `p-tab`, which would otherwise cancel its click.
- Without `ids`: shows a single "New `<entityName>`" tab (`EntityTab` with `entity: undefined`) and renders the template with `undefined`, so the form is empty. Create mode has a tab too, so the layout does not jump when saving turns it into the record's tab. Its × cancels creating: it goes to `listPath`, asking first if the form has changes. Create mode never mixes with open records: the tab list is either the one new tab or the loaded records.
- Save appears while any open form or part is dirty. In edit mode it validates only the dirty forms (`EntityForm.validValue`); in create mode it always validates the new form, because the record must exist before its parts can be saved. If one is invalid, nothing is sent and its tab is shown.
- A part (`EntityEditPart`: `entityId`, `dirty`, `save(entityId)`) is anything besides the form that holds pending changes for a record and saves them only on Save, so every write of an edit page goes through the Save action. Parts connect through DI (`connectPart` / `disconnectPart`), like forms, so `EntityEditPage` stays generic (today the only part is `ImageUpload`). Updating saves the dirty forms, then every dirty part with its own record id, then reloads. Creating creates the record, then saves the dirty parts with the new id before reopening it; a failed part does not undo the create. A tab whose part is dirty asks before closing, like a dirty form.
- Creating calls `writer.create(value)` and reopens the same route with `?ids=<new id>`. Updating calls `writer.update(changes)` once with every changed record (`EntityChange`: the loaded entity and the form value), which maps them to one bulk PUT (all or nothing), then reloads the records.
- `EntityForm` connects itself to the enclosing `EntityEditPage` through DI (`connect` / `disconnect`) and reports `dirty`, so entity forms need no create- or update-specific code.
- Product attribute fields live in `products/product-attributes-fields` (`app-product-attributes-fields`). `ProductForm` owns the `attributes` `FormRecord` and passes it in with the selected type; the component builds the fields from the selected type's definitions (`GET /api/product-types`): whole numbers use `app-number-field`, text uses `app-text-field`, with `required` / `min` / `maxLength` from the definition. Switching type keeps values of attributes both types share.

### Images live in `ImageUpload`

`shared/image-upload` (`ImageUpload`, `app-image-upload`) holds everything about an entity's images and is generic, like the images API (`entityType` + `entityId`); `EntityEditPage` knows nothing about images. The edit page passes `entityId`, `savedImages` and an `ImageWriter` (`upload`, `delete`, `reorder`) built from its feature service, as `EditProductsPage.productImageWriter` does with `ProductsService`. Writes follow the action menu like everything else: new images are saved by Save and removed by Delete; only reordering saved images is sent straight away, because it is a view arrangement rather than new data:

- The gallery is one grid: the image cards, then an "Add images" upload card that always stays last (it is a disabled `cdkDrag`, and `keepsUploadCardLast` stops images from being sorted into its slot). Clicking it opens the file picker; files can also be dropped anywhere on the gallery.
- Choosing or dropping files only stages them, on new and saved records alike: they appear as cards at once (object-URL previews, `id` `staged-N`, `stagedFile` set), the component turns `dirty` and Save appears. The component is an `EntityEditPart`: its `save(entityId)` uploads the staged files in one request (so at most 10 can be staged) and, if the user dragged staged cards between saved ones, sends one `reorder` with the final order. The page then reloads or reopens the record, and `images` (a `linkedSignal` of `savedImages`) resets to the saved list, which drops the staged entries.
- Rejected files are never shown inside the component: FileUpload's own type and size messages (worded through its `invalidFile*Message*` inputs) are moved into the global error toast via `AppMessageService.error` ("Image not added", one toast per file), and the component checks the 10-files-per-upload limit itself, because FileUpload adds that message only after `onSelect`.
- Dragging changes the order on screen at once. If the order of the saved images changed, it calls `reorder` straight away with the saved ids only (`PUT /api/images/order` must list exactly the current saved images) and puts the old order back if the request fails; staged images are placed on Save.
- Selecting images shows Delete in the action menu, registered by the component itself; holding it calls `delete` for the selected saved images without a confirmation dialog (the nav menu's busy ring spins until the request ends) and drops selected staged images locally.
- A new record shows the gallery from the start, so images can be added together with the description; Save creates the record first and then uploads them. A failed image upload does not undo the create: the request error toast shows, the record reopens without those images, and the user adds them again.
- Each card shows the image's original `fileName` (stored by the API on upload). Images uploaded before the API stored names have an empty `fileName` and show "Image N" (their position) instead.

Today only products use it; orders and customers have no images. To add images to another entity, give its service the three image calls and pass a writer the same way.
